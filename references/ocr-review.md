# open_code_review_ocr 深度评审口径

本地基线依据 `ai_code_review_ocr` 提交 `f8252facf359c1f65d679b2662583504717269ee` 的 `engines/ocr/upstream/internal/productadapter/guidance/review-policy.md`（`review-value-v2`）和 `packages/review_application/reference_score.py`（`ocr-commit-risk-v1`）。该仓发布记录显示 043 兼容升级已部署，记录中的实际策略是 `legacy`；`behavior_delta_v1` 作为候选策略存在。本参考提取现行通用取证和评分口径。

## 从变更一路核对到结果

1. 先确定本次改变的操作、合法输入及原先承诺的结果。对照被替换或删除的旧路径，依次检查校验、上下游传递、状态、异步回调、持久化或释放，以及最终可观察结果。保留实际读过的新旧文件和行号。
2. 优先核实能改变结论的决定性条件。例如删除了局部保护时找等价保护，新增字段时看两侧实际序列化布局，改签名时找适用调用方或构建分支。有反证就撤回原假设；未读决定性实现时只说明剩余核对项。
3. 复核时重新读取决定性来源，核对新旧归因、可达前提和实际后果，并尝试找反例。确定在变更前已存在且触发和后果都未改变的缺陷留作正常评审背景。已查清局部行为只差外部约定时，写清可观察变化、条件后果和唯一待确认的外部事实。
4. 按根因报告，保留各处关键证据。一个局部缺陷也可报告，只需如实说明影响。纯风格意见、泛化重构、缺测试本身和缺材料本身不作为 OCR 主报告缺陷。

## 何时给 OCR 本地参考分

需要确认本次完整变更清单、各相关变更材料均已调查，并且待验证候选已完成独立复核。可用的独立复核需要从可信材料重新建立证据链并尝试反证，例如宿主提供的独立复核结果。常规自查能提高发现质量，单一上下文中的重复确认不能充作独立复核。给分时只纳入已复核、代码证据支持且归因为本次变更引入的问题。

范围、调查、候选复核或关键业务前提仍不完整时，交付已有问题和缺口，OCR 整笔参考分暂缺。完成后按阻断、严重、一般、轻微档位计算，见 [本地计分说明](scoring.md)。普通预估分单独计算。
